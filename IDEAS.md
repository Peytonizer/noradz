# Ideas

Blue-sky backlog for noradz.io. Nothing here is committed to — it's a holding pen so good
ideas don't evaporate between sessions.

Kept separate from `noradz-site-spec.md` on purpose: the spec is the frozen v1 build record
(what was designed and shipped), the README describes what exists now, the CHANGELOG records
what happened. This file is the only one allowed to be speculative.

## Constraints worth keeping

These aren't rules, but breaking one should be a deliberate decision, not a drift.

- **No build step for as long as possible.** Plain HTML/CSS on GitHub Pages is the whole
  reason this site is cheap to maintain. If something genuinely needs generating, prefer a
  GitHub Action that pre-renders static HTML at deploy over shipping a client-side framework.
- **One accent colour.** Red = Ra-Kacharz, near-black = citizens. A second accent colour
  breaks the only visual idea the site has.
- **Honest over impressive.** The site's premise is a working log, not a portfolio. Failures
  and abandoned builds are on-brand; inflated claims aren't.
- **Not a contact channel.** Deliberate omission in v1 — keep it that way unless that changes.

---

## 1. Surviving more than three projects

The grid assumes three cards in a row. This breaks first, and probably soon.

- **Project detail pages** (`/work/<slug>/`). Each project gets a page: what it does, why it
  was built, what broke, what was learnt, screenshots, current status. The homepage grid
  becomes an index of the three or four most recent, with an "all work" link. This is the
  single highest-value structural change and everything else in this file gets easier once
  it exists.
- **Client-side tag filter.** The tag pills already exist and do nothing. Making them
  clickable filters (`python`, `client-side`, `desktop`…) is ~30 lines of vanilla JS and no
  build step. Cheap win once there are enough cards to need it.
- **A status taxonomy, shown honestly.** `live` / `shipped` / `classified` / `retired` /
  `half-built`. The `classified` badge is already the first member of this set. A small
  legend in the footer explains them.
- **The graveyard.** A separate, lower section for experiments that died, each with a
  one-line post-mortem ("worked, but nobody needed it"). Most random AI projects don't ship,
  and pretending otherwise makes the site a portfolio instead of a log. Probably the most
  distinctive thing this site could do.

## 2. Making it a log, not a shopfront

The subhead promises "a working log". Right now it's a static list — this closes that gap.

- **`/log` — dated short entries.** One per interesting build session, failure, or decision.
  Doesn't need to be long-form blogging; three sentences and a code block is enough. Aim
  for something that's still worth reading in a year.
- **RSS or JSON feed** for the log, so it can actually be followed. Hand-writable if entries
  are added one at a time, or generated by the same Action that renders the log.
- **A `/now` page** (nownownow.com convention) — what's being built this month, updated when
  it changes and left stale-with-a-date when it doesn't.

## 3. Automation — the site as its own AI project

Right now every project card is hand-written HTML. That's fine at three and painful at ten.

- **`projects.json` as the single source of truth**, rendered to static HTML by a GitHub
  Action on push. Adding a project becomes a data edit, not a markup edit, and the same data
  feeds the grid, the detail pages, the tag filter and the feed.
- **Live repo stats via the GitHub API.** A scheduled Action writes last-commit dates,
  languages and repo sizes into a JSON file that the build reads: "last touched 3 days ago"
  on each card. Makes the site feel alive with no server and no runtime API calls.
- **Make the nav status dot mean something.** It's currently decoration. A scheduled health
  check that pings each live project and writes a status file would turn it into a real
  indicator — and if something's down, the dot going red is a genuinely useful signal.
- **Link checker + HTML validation in CI.** Boring, but a dead link on a portfolio site is
  the kind of thing that goes unnoticed for months.

## 4. AI-native ideas — eating the dog food

A site about building things with AI should be visibly built with AI. These are the ideas
that would make it more than a generic project index.

- **A build ledger per project.** Which model built it, roughly how many sessions, rough
  token cost, how much was hand-edited afterwards. Almost nobody publishes this and it's the
  most genuinely interesting data this site is sitting on. Fits the "kept honest" line exactly.
- **Publish the specs.** `noradz-site-spec.md` produced this site; other projects have
  equivalents. Shipping the spec next to the thing it produced ("here's the prompt that
  built this") is a real artefact, not a gimmick.
- **`/llms.txt`** — a machine-readable summary of the site and its projects for AI crawlers.
  Low effort, and a site about AI projects serving one is quietly funny.
- **Ask-the-site.** A small chat over the project descriptions. Worth wanting, but note the
  catch: it needs an API key, which means a proxy (Cloudflare Worker or similar) and a
  spend cap — it can't be static, and the key must never land in this repo. Treat as a
  deliberate architecture decision, not a quick add.
- **Generated OG images per project**, produced by a script at build time so sharing a
  project link doesn't show a blank card.

## 5. Craft and polish

- **Open Graph / Twitter card meta is missing entirely.** Any link to noradz.io currently
  previews as bare text. This is the biggest small gap on the site right now.
- **Command palette (⌘K)** to jump between projects and sections. Fits the terminal aesthetic
  better than it fits most sites, and works fine as vanilla JS.
- **View transitions** between the index and detail pages once those exist — CSS-only via the
  View Transitions API, gated behind `prefers-reduced-motion`.
- **More lore easter eggs.** The footer line is the only one. Typing `noradzeer` opening a
  small console, or a "cleanliness mode" light theme as a joke about the food-purity rule,
  both extend the bit without explaining it.
- **Accessibility and Lighthouse pass**, ideally as a budget in CI so it can't regress.
- **Privacy-respecting analytics** (GoatCounter, Plausible, Cloudflare). Only worth it to
  answer a real question. Note the CLAUDE.md rule: no analytics IDs in the repo if they're
  meant to stay private.

## If only one thing gets done

Project detail pages driven by `projects.json`, with OG meta. That unblocks the log, the
feed, the tag filter, the graveyard and the build ledger — everything else here is
downstream of having somewhere to put more than one paragraph per project.
